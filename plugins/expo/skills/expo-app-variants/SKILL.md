# Expo App Variants

Install several builds of one project side by side on a device. Each variant gets its own native identity, so installing one no longer replaces another.

**The variants are the project's choice** — how many, and what they are called. The examples below use `development`, `preview`, and `production` because those names line up with EAS defaults. Read every example as a shape to adapt: one case per variant the project actually has. The "Naming variants" section covers other names and counts.

## The model: identity vs environment

**Identity** — `ios.bundleIdentifier` and `android.package`, baked into the native build. A device keeps one app per identifier, so per-variant identifiers are what let builds coexist.

**Environment** — the variables loaded when the app config is evaluated (API URL, keys).

Changing identity requires a custom build, local or on EAS Build. `expo start` cannot change it, and Expo Go runs every project under one identity.

## Ground rule: ask before any command that writes to EAS

Read-only commands run freely: `eas env:list`, `npx expo config`. Every command that creates or changes state on the EAS servers — `eas env:set`, `eas update:configure`, `eas build`, `eas update` — needs the user's explicit OK first, every time. State in one sentence what the command will do, then ask. Editing local files (`app.config.ts`, `eas.json`, `package.json`) follows the normal flow and does not need this extra confirmation.

## Step 0: detect, then ask

Do not open with a questionnaire, and do not propose a rewrite of something that already works. Read the project first and answer what you can.

| Check | Where | What it settles |
| --- | --- | --- |
| Config style | `app.json`, `app.config.ts`, `app.config.js` | Extend the dynamic config, or add one |
| Native directories | Are `ios/` or `android/` committed to git? | Whether the CNG gate below stops the recipe |
| Identity already varying | Does the config branch on any env var for `bundleIdentifier` / `package`? | Whether this is a new setup or a gap-fill |
| Current identity | `ios.bundleIdentifier`, `android.package` | The prefix(es) to reuse — never invent one, and never unify the platforms if they differ. A platform with no identifier stays out of the config |
| Variant variable name | The env var the config already reads | Reuse it; do not rename to `APP_VARIANT` |
| Existing profiles | `eas.json` → `build` keys, and their `env` / `environment` / `channel` | Which profiles to extend |
| Variables on EAS | `eas env:list --environment <env>` | Whether EAS environments are already in use |
| Dev client installed | `expo-dev-client` in `package.json` | Whether Step 3 applies, and whether a profile with `developmentClient: true` can build |
| EAS Update in use | `expo-updates` in `package.json`, `updates.url` in the config | Whether Step 5 applies at all |
| Icons in use | `icon`, `ios.icon`, `android.adaptiveIcon` | Which icon fields `getIcon()` must override, and whether `ios.icon` is a flat image or a `.icon` bundle |
| Custom scheme | `scheme` in the app config | Whether to offer Step 3's per-variant scheme |

If `eas env:list` fails or is not authenticated, note it and continue. Do not stall and do not prompt the user to log in.

**CNG gate.** This skill assumes CNG: native directories generated by `npx expo prebuild` and gitignored. If `ios/` or `android/` are committed and carry manual native changes, stop before applying any recipe — `prebuild --clean` deletes those changes. Such a project needs Android product flavors and iOS targets or schemes instead, which is outside this skill. Say so, and point to the
[app variants doc](https://docs.expo.dev/build-reference/variants.md).

### If variants are already set up

When the config already branches to give each variant its own identity, the core work is done. **Do not restructure it.** Do not rename their variable, reshape their `if`/ternary into a `switch`, move values between files, or align their names to this skill's examples. A working setup that differs from the shapes below is not a defect.

**Settle storage first.** "Already set up" covers identity, not storage. If no profile carries `APP_VARIANT` — no `env` block, and no `environment` key backed by an existing EAS variable — then question 1 below is still open. Ask it before offering any alignment gap, because adding `environment` keys chooses the EAS-environments storage.

Then report what exists in one or two lines, and offer only the missing pieces:

| Already present | Gap to offer |
| --- | --- |
| Identity varies per variant | Core setup is done — say so |
| No `addGeneratedScheme` guard | Step 3, if `expo-dev-client` is installed |
| One `scheme` shared by every variant | Step 3's `getScheme()`, if the config sets a `scheme` |
| Same icon for every variant | Step 4 |
| Profiles set `env` but no `channel` | Step 5, if the project uses EAS Update |
| Profiles have `channel` but no `APP_VARIANT` source | Ask question 1, then apply Step 2 in full |
| EAS environments in use, but profiles have no `environment` key | Step 2 — set it on every profile. EAS defaults exist, but they follow `distribution` and `developmentClient` flags, not profile names |
| `env` blocks duplicated across profiles | Offer the move to EAS environments (Step 2), as an option |
| A profile sets `developmentClient: true` but `expo-dev-client` is not installed | Offer `npx expo install expo-dev-client`, or drop the flag — interactive builds prompt for it, non-interactive (CI) builds fail |
| No external service registration per identifier | Step 6 |

Present the gaps as a short list and let the user pick. Skip any step they decline.

### Questions for a new setup

Ask the user — with the environment's structured question tool if one exists (`AskUserQuestion` in Claude Code), otherwise in plain text — and only what detection did not settle. Skip the block if the request already stated the choice.

**Keep every prompt short.** One plain sentence per question, one line per option. No SDK rules, no command names, no failure scenarios inside a prompt — compressing mechanics into a question makes it scary and easy to get wrong. The user can ask why, and then the agent explains from the skill body.

1. **Where should `APP_VARIANT` live?** Ask this first. The whole prompt:

   > Where should the APP_VARIANT variable live?
   > - **EAS environments (Recommended)** — one value, stored on EAS; builds and updates read it directly, local commands use a pulled copy.
   > - **In the repo** — `env` blocks in `eas.json`, plus `.env.local` for local commands.

   Nothing more in the prompt. Then:
   - **EAS environments** → the recommended Step 2, in full: create the variables (ground rule applies), set `environment` on every profile, pull locally.
   - **In the repo** → the alternative Step 2. If the project uses EAS Update, push back once, in one sentence: on SDK 55 or later, `eas update` reads variables only from EAS environments. Then respect the answer and state that boundary in the summary.

2. **Which variants, and what are they called?** This is the user's decision. Suggest, do not impose.
   - `development` + `preview` + `production` — suggest this first; one name then carries through profiles, environments, and channels (see "Naming variants").
   - `development` + `production` — fewer identifiers to register and maintain.
   - A custom set — any names, any count. Take the list the user gives and use it verbatim.

   Accept whatever they answer, including a set that matches none of the options. If `eas.json` already defines profiles, offer those names as the default rather than these. Then carry the chosen list through every later step: one `case` per variant, one build profile per variant, one channel per variant.

   Read the "Naming variants" section below before recommending a custom set, since two constraints apply.

3. **Which extras?** Multi-select, and offer each item only where it applies:
   - Per-variant icons — always offer.
   - Per-variant URL scheme (Step 3) — offer only when the config sets a `scheme`. One line on the cost: each variant's scheme must be registered wherever the base scheme is, OAuth redirect allow-lists most of all.
   - EAS Update channel alignment (Step 5) — offer only when the project uses EAS Update **and** question 1 chose EAS environments. On the repo track there is no `environment` key to align, so do not offer it. Pre-select it when the profiles already set `channel`.

   Step 3's guard is not an extra to ask about: apply it whenever `expo-dev-client` is installed.

4. **Add a static `app.json` too?** Ask this only when the project has a dynamic config and no `app.json`. Variants work fine without one, so this is an offer, not a fix. The prompt options, one line each:
   - *Add `app.json` as a base layer (Recommended)* — Expo tooling can write generated values into it automatically.
   - *Keep the dynamic config alone* — one file, nothing to keep in sync.

   The reason behind the recommendation, for when the user asks: tooling updates static configs but not dynamic ones, so `eas build:configure` and `eas update:configure` write generated values (project ID, updates URL) into `app.json` instead of asking the user to paste them by hand.

   Variants work the same either way, so do not argue if the user prefers the single dynamic config. If they accept, move only the stable values into `app.json`; anything computed at config time, variant-dependent or not, stays in `app.config.ts`. Adding `app.json` means `app.config.ts` must export a **function** from then on.

If the user declines to answer, proceed with EAS environments and the three suggested variants, and leave the config layout as it is. The ground rule still applies — `eas env:set` waits for an explicit OK. Say which defaults were used, so the variant list is visible and easy to correct.

## Step 1: a config that reads `APP_VARIANT`

A static file holds one identifier, so variants need a config that reads a variable. That means a dynamic `app.config.ts` (or `.js`). Which file to touch depends on what the project has.

**Already has `app.config.ts` or `app.config.js`** — add the helpers to it. Nothing else needs to change. Do not add an `app.json` unless the user asked for it in Step 0 question 4. Use Recipe 2 in [`./references/config-recipes.md`](./references/config-recipes.md) when there is no `app.json`, or Recipe 1 when there is.

**Has only `app.json`** — add `app.config.ts` beside it, per Recipe 1 in
[`./references/config-recipes.md`](./references/config-recipes.md). Expo reads `app.json` first, hands it to the dynamic config as `{ config }`, and uses what the dynamic config returns. So `app.json` stays the base layer and `app.config.ts` is a thin override. Converting fully to one dynamic file is also fine if the user prefers it.

Keeping both files is the recommended default, not a requirement. Either layout is a complete, supported setup for variants.

**When an `app.json` exists, the dynamic config must export a function.** A default-exported plain object makes Expo ignore `app.json` entirely. With no `app.json`, a plain object export is fine.

The example below uses the three suggested variants. Write one `case` per variant the project chose in Step 0.

```ts
import { ExpoConfig, ConfigContext } from "expo/config";

const APP_ID_PREFIX = "com.myapp"; // take this from the identity detected in Step 0

function getAppId() {
  switch (process.env.APP_VARIANT) {
    case "production": return APP_ID_PREFIX;
    case "preview": return `${APP_ID_PREFIX}.preview`;
    default: return `${APP_ID_PREFIX}.dev`;
  }
}

function getName(base: string) {
  switch (process.env.APP_VARIANT) {
    case "production": return base;
    case "preview": return `${base} (Preview)`;
    default: return `${base} (Dev)`;
  }
}

export default ({ config }: ConfigContext): ExpoConfig => ({
  ...config,
  slug: config.slug ?? "my-app", // required by ExpoConfig, optional on the incoming Partial
  name: getName(config.name ?? "MyApp"),
  ios: { ...config.ios, bundleIdentifier: getAppId() },
  android: { ...config.android, package: getAppId() },
});
```

`ConfigContext.config` is a `Partial<ExpoConfig>`, so `name` and `slug` arrive as `string | undefined` while the `ExpoConfig` return type requires both. Under the `strict: true` that Expo templates ship with, omitting the `slug` fallback is a type error. `app.json` supplies the real values at runtime.

`APP_ID_PREFIX` assumes iOS and Android share one identifier, the common case. When the detected `ios.bundleIdentifier` and `android.package` differ, keep two constants — one per platform — and derive each platform's variant identifiers from its own. Never unify existing identifiers: for a shipped app, that changes its published identity on one platform.

When only one platform has an identifier, vary that platform and leave the other out of the config entirely. An `app.json` with `ios.bundleIdentifier` and no `android.package` is the common shape, and setting `android.package` from the helper would give that project an identity it never had — an invented one, which the rule above forbids. Drop the `android` block instead, so `...config` carries Android through untouched. Varying a single platform is a complete setup, not a partial one.

When there is no `app.json`, drop the `ConfigContext` parameter and the spreads, and return the whole config directly. See [`./references/config-recipes.md`](./references/config-recipes.md) for that form.

Spread `...config` at every level you touch. Forgetting it at the top drops everything in `app.json`; setting `bundleIdentifier` without spreading `config.ios` keeps the new ID but loses the rest of `ios`.

A missing `APP_VARIANT` falls through to development on purpose. `expo start`, `expo run`, and `expo prebuild` never ask which variant, so whatever the default is, that is what local work gets — and production identity should only come from asking for it. Note that a misspelled value lands in `default` too — the Verify loop below makes that visible, since the misspelled variant prints the dev identity.

**This step is the same whichever Step 2 you take** — `app.config.ts` only reads `process.env.APP_VARIANT`, so the storage choice stays reversible.

### Naming variants

`APP_VARIANT` and every variant name and count are conventions. Suggest `development` / `preview` / `production` because they match the profiles `eas build:configure` creates and the three built-in EAS environments; adopt whatever set the user names. Adding a variant is one more `case`, one more build profile, one more channel. Renaming one means renaming all three together.

Two constraints to state when someone wants a different set:

- **Environments cannot be renamed on every plan.** Only `development`, `preview`, and `production` are built in; custom environments need a Production or Enterprise plan. Build profiles and update channels have no such limit, so name those freely. The names are a **mapping, not an equality** — a `staging` variant can map to the built-in `preview` environment. With a custom set, write the mapping down, one line per variant, and use it in every later command:

  | Variant (`APP_VARIANT`) | Build profile | EAS environment | Update channel |
  | --- | --- | --- | --- |
  | `staging` | `staging` | `preview` | `staging` |

  Publishing names the mapped pair — `eas update --channel staging --environment preview`. One limit follows: each environment holds one `APP_VARIANT` value, so without custom environments at most three variants can store their value on EAS.
- **Each variant costs setup:** its own service registrations (Step 6), its own icon, and its own store entry if it ships. Say this when the user wants a long list.

## Step 2 (recommended): `APP_VARIANT` as an EAS environment variable

**Apply this step as one unit** — `eas env:set` writes to the EAS servers, so the ground rule applies. `environment` keys without the variables are worse than nothing: every EAS build then evaluates the config with `APP_VARIANT` unset and silently gets the development identity, production included. Create the variables first, then point the profiles at their environments.

Create the variable once per environment, then have each build profile name its environment instead of spelling out variables:

```sh
eas env:set --name APP_VARIANT --value development --environment development --visibility plaintext
# repeat per variant: --value is the variant name, --environment its mapped environment
# (the same name in the default 1:1 setup — see "Naming variants" for custom mappings)
```

```json
{
  "build": {
    "development": { "developmentClient": true, "environment": "development" }
  }
}
```

Set `environment` explicitly on **every** build profile, including simulator profiles and profiles that never publish updates. A profile without the key still gets one — EAS Build picks a default: `production` when `distribution` is `store`, `development` when `developmentClient` is `true`, otherwise `preview`. Those defaults follow flags, not the profile's name, so a `staging` profile that submits to the store would silently load the `production` environment. Explicit keys keep the chain visible. A profile that `extends` another inherits its `environment`.

Do not leave both `env` and `environment` setting `APP_VARIANT` in the same profile. Pick one. `developmentClient: true` belongs only in projects with `expo-dev-client` installed — without it, interactive builds prompt to install the package and non-interactive (CI) builds fail.

Locally, `eas env:pull --environment development` writes `.env.local` (override with `--path`), so `expo start`, `expo run`, and `expo prebuild` all read the variable with nothing inline. Pull again when switching variants, so `.env.local` always matches the variant being worked on.

**The pull replaces `.env.local` rather than merging into it.** Before the first pull, read any existing file and account for every key in it: a key that no EAS environment holds is gone afterwards, and the only trace is a `Reused local values for following secrets:` line, which covers secrets alone. A local-only debug flag is the usual casualty, and losing it is silent — the app just takes its default branch on the next run. Store such keys in the environment so every later pull returns them, or add them back by hand once the pull is done.

Publishing an update reads the same environment. **On SDK 55 or later, `eas update` requires `--environment`; with an environment set, it reads only the EAS environment variables and ignores local `.env` files.** Later steps refer back to this rule.

```sh
eas update --channel preview --environment preview
```

Custom environments beyond the built-in three require a Production or Enterprise plan.

## Step 2 (alternative): `APP_VARIANT` without EAS environments

Use this when question 1 chose the repo. A project that does not build on EAS skips the `eas.json` part entirely — only the local commands below apply.

**Builds** — an `env` block per profile in `eas.json`. A profile that uses `extends` inherits it:

```json
{
  "build": {
    "development": { "developmentClient": true, "env": { "APP_VARIANT": "development" } },
    "preview": { "distribution": "internal", "env": { "APP_VARIANT": "preview" } },
    "production": { "autoIncrement": true, "env": { "APP_VARIANT": "production" } }
  }
}
```

**Local commands** — that `env` block applies only to `eas build`. `expo start`, `expo run`, and `expo prebuild` never see it. Put the variable in `.env.local`, which those commands read automatically:

```sh
# .env.local — gitignored in Expo templates
APP_VARIANT=development
```

A missing file falls through to the development identity, so day-to-day work needs no file at all. Edit the value to work on another variant, then run `npx expo prebuild --clean` when the native project should switch identity.

**Never suggest the inline `APP_VARIANT=value expo start` form.** It fails on Windows `cmd.exe`, and it scatters the variant across commands instead of keeping it in one visible place.

One boundary: the SDK 55 `eas update` rule from the recommended Step 2 still applies. A project that publishes updates on SDK 55 or later needs `APP_VARIANT` in the EAS environments even if its builds keep using `env` blocks. On SDK 54 or earlier, set the value in `.env.local` before publishing.

**Moving to EAS environments later** means creating the variables and swapping `env` for `environment`. Moving back means writing the values into `eas.json` and `.env.local` again. `app.config.ts` is untouched either way.

## Step 3: one URL scheme per variant

Two schemes reach an installed variant, and each needs its own treatment.

**The dev-server link.** When `expo-dev-client` is installed, add this. Do not ask first, and do not explain it at length:

```ts
plugins: [
  ["expo-dev-client", { addGeneratedScheme: process.env.APP_VARIANT === "development" }],
],
```

One sentence for the user is enough: it makes the development build the only app that answers the `exp+<slug>` link behind the dev server's QR code. Variants built before this change still answer the link — rebuild them or remove them from the device.

"Do not ask" applies to a new setup, where the config is being written anyway. On an existing setup, the guard is offered through the Step 0 gap list like every other gap.

Skip the guard when `expo-dev-client` is not installed.

**The project's own `scheme`.** When the config sets one, offer a per-variant scheme through the extras question — unlike the guard, do not apply it unasked. Shared, every variant registers the same `myapp://` and the OS resolves it to whichever install it prefers; the guard above covers only `exp+<slug>`, so a gated `addGeneratedScheme` still leaves one `scheme` pointing at three apps. Derived, each variant's scheme must be registered wherever the base scheme is — OAuth redirect allow-lists are the usual case, and a missed registration breaks sign-in on that variant. That external cost is why this is the user's call. If they accept, derive the scheme in the same switch shape as the identifier, with `getScheme()` from [`./references/config-recipes.md`](./references/config-recipes.md). A project whose config sets no `scheme` needs nothing here.

## Step 4: per-variant icons

Add a `getIcon()` helper in the same switch shape, returning `undefined` for production so the `app.json` icons flow through untouched, and a flat image for the other variants.

`ios.icon` and `android.adaptiveIcon.foregroundImage` take precedence over the top-level `icon`, so override those along with `icon` and `android.icon`, each with `icon ?? config.<field>` to keep the type as `string`. Full helper in [`./references/config-recipes.md`](./references/config-recipes.md).

You cannot draw the images. Tell the user which files to add — the same icon with a different background color is enough.

**Icon Composer bundles are the exception, and the agent can finish them alone.** Since SDK 54, `ios.icon` also accepts a `.icon` bundle: a directory holding `icon.json` and an `Assets/` folder. Copy the directory once per variant and change the background `fill` in each copy's `icon.json`, which needs no image editing. A `.icon` directory is valid for `ios.icon` only, so that project needs a `getIosIcon()` returning bundle paths, separate from any flat image the other icon fields take. Detect which form applies from the `ios.icon` value in Step 0: a path ending in `.icon` is a bundle, a path ending in `.png` is a flat image.

## Step 5: match EAS Update channels

Only relevant when the project uses EAS Update — `expo-updates` in `package.json`, or `updates.url` in the app config. Skip it otherwise, and do not add `channel` to the profiles of a project that never publishes updates.

`eas update:configure` does most of the setup: it adds `updates.url` and `runtimeVersion` to the app config and a `channel` to the `preview` and `production` build profiles. Let it do that work, and add a matching `channel` by hand on any other profile that should receive updates. What is left to sort out is the environment — each profile's `channel` should sit next to its mapped `environment` from Step 2, so the whole chain lines up. The `preview` variant is built by the `preview` profile, loads the `preview` environment, and receives updates on the `preview` channel:

```json
{
  "build": {
    "preview": { "environment": "preview", "channel": "preview" }
  }
}
```

Publishing names both. Pass `--environment` for the channel's **mapped** environment — the same name in the default setup — required on SDK 55 or later (the Step 2 rule), and recommended on older SDKs so builds and updates read the same values:

```sh
eas update --channel preview --environment preview
```

The channel routes the update; the environment decides which values it carries. A mismatched `--environment` ships the wrong values to existing installs with no error.

Without EAS environments there is no `environment` to align — see the publishing boundary at the end of the alternative Step 2.

## Step 6: flag the per-variant service registrations

A new identifier is not a new registration. `APP_VARIANT` can change the bundle identifier, but it cannot create the external registrations that identifier needs. Creating them is the user's task — it happens in service dashboards (Firebase, Google Cloud, App Store Connect), not in the repo. **Do not invent API keys or placeholder credential files to fill the gap.**

What the agent can do is detect and report. Check the config and dependencies for anything keyed on the bundle id or package name — `android.googleServicesFile`, `ios.googleServicesFile`, Maps API keys, push setup — and list the per-variant registrations the user needs: either a separate app per identifier, or another allowed identifier under the same project. Google Maps and Firebase Cloud Messaging are the usual examples.

Once the user has the per-variant files or keys, wire them the same way as every other value: switch them in `app.config.ts`. For Firebase on Android that is `android.googleServicesFile` per variant, with the file supplied as an EAS file environment variable or as one committed path per variant. Do not place files under `android/app/src/{flavor}/` — that layout is for bare projects with committed native directories and Gradle flavors, and `npx expo prebuild --clean` deletes it in a CNG project.

## Verify

Print the fields the project actually varies. The filter below covers both platforms; drop `.android.package` for an iOS-only project, so a `null` never has to be read as a pass.

```sh
npx expo config --json | jq '.name, .ios.bundleIdentifier, .android.package'   # default → dev identity
for v in development preview production; do   # the project's variant list
  APP_VARIANT=$v npx expo config --json | jq -c '{name, id: .ios.bundleIdentifier, pkg: .android.package}'
done
```

Inline variables are fine for these one-off checks — they override `.env.local` for that single command. The daily workflow keeps the variant in `.env.local` or in EAS environments, never inline.

One distinct identity per variant, on every platform the project varies, means Step 1 works. Confirm the default run shows the dev identity and that nothing from the previous config went missing.

With EAS environments, also confirm the variables exist on the servers — `APP_VARIANT` must appear in every environment that `eas.json` references:

```sh
eas env:list --environment development   # repeat per environment
```

After a rebuild, both apps should be on the device with distinct names and icons.

## Pitfalls

- Rewriting a working variant setup to match this skill's shape. Only fill gaps. See Step 0.
- Adding an `app.json` to a project that deliberately has only a dynamic config.
- Forgetting `...config` or `...config.ios` silently drops config. Diff `npx expo config` before and after.

Everything that breaks after setup is in the symptom table:
[`./references/troubleshooting.md`](./references/troubleshooting.md).
